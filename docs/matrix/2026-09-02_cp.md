# CP 用例重跑（2026-09-02）

`2026-09-01_triton.md` 里 12 个 CP 格全红，归因 `CANN`，note 说"CP 必须配 FlexAttention，
而它的 document mask 需要 910B2 没有的间接寻址"。**那个归因是错的，原因在我们自己**：
`npu_minimal` 先把 flex 转成 varlen，才撞上上游 `models/common/decoder.py:186` 的
`NotImplementedError: Context Parallel is not supported with ScaledDotProductAttention
or VarlenAttention`。芯片从头到尾没参与。

torch 对 CP 只实现了两种注意力：flex（`_ContextParallel.flex_input_fn` 把 K/V
all-gather 上来）和 SDPA（ring attention）。转成 varlen 之后两个钩子都挂不上，所以
转换在 CP 下只能把能跑的变成跑不了的。修复：`recipes/deltas.py::flex_to_varlen`
在 `context_parallel_degree > 1` 时直接返回，不转。

## 结论要收紧：CP 不是"解锁"，是从硬拒绝变成显存受限

三个 OOM 都是同一个数字——单次要 10.00 GiB，已分配 48.84 GiB。这就是 **eager flex
实体化 O(T²) 分数矩阵**的代价。CP 下序列已分片，每张卡扛 O(T²/cp)，所以 CP 度高的布局
（`fsdp+tp+cp`、`validation_tp_cp_pp`）装得下，而 CP 度低、大头给了 dp_shard 的布局
（三个 `*hsdp*cp*` / `fsdp+cp`）装不下。

**为什么是 eager flex，而不是我们的融合算子**：torch 的 CP 只认 flex 和 SDPA；
编译版 flex 在 910B2 上编不出 document mask（硬件门）。所以 CP 目前只剩 eager flex。
正确的终局是让 CP 走 `npu_fusion_attention`——细节与工作量估计见
`docs/capability-matrix.md` 的 CP 那一节。

## 过程中修掉的三个工具缺陷

这轮扫描本身暴露了三个会污染结论的问题，都已修并带测试：

1. **runner 不钉解释器**。`run_train.sh` 用 PATH 里的 `torchrun`，第一次启动没带 venv，
   13 格全红在"0 active drivers"。改成 `PYTHON` + `python -m torch.distributed.run`。
2. **HARNESS 假红不重试**。三格死在上一格残留的 HCCL 端口（`port 16666 have already
   been bound`），triage 的 note 一直写着"rerun"却没人重试。重跑后两格转绿，一格是
   预期的 helion 缺失。现在 HARNESS 会自动重试一次。
3. **triage 缺 OOM 规则，且 UNKNOWN 会捡到已恢复的 WARNING**。torch_npu 每步都打
   `NPU streaming create_block_mask failed; falling back ...: TypeError`（那是 NPU-12），
   它盖过了真正的 `OutOfMemoryError`。新增 `OOM` 码，UNKNOWN 兜底跳过声明已恢复的行。
