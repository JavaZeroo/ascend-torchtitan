§1定位与设计目标

ascend-torchtitan 是 torchtitan 的树外昇腾 NPU 扩展：torchtitan 按 commit SHA 作为已安装依赖固定，本仓绝不 fork、绝不改上游检出（ADR-001）。项目同时追三个快速移动的上游 —— torch nightly、torch_npu master（源码构建）、torchtitan main —— 因此真正的设计难题不是"写内核"，而是：

  • 薄。本仓与上游之间的每一处接触都必须可枚举、可审计、可删除。补丁数量本身是健康度指标，目标趋近于零。
  • 归因准确。一个用例失败，必须能回答"这是谁的问题"：torchtitan、torch、torch_npu、CANN、三方依赖，还是我们自己。能力矩阵的红格如果分不清责任方，就没有价值（P12）。
  • 缺陷回流上游。torch_npu 的问题只能修、不能绕（P1/P9，项目红线）；修复以 patch + gitcode issue/PR 的形式送回 gitcode.com/ascend/*，合入即删。
  • 响亮失败。基础依赖（torch / torch_npu / torchtitan）硬导入、绝不 try（P14/ADR-007）；降级只允许发生在真正可选的加速包上，且必须 WARNING + provenance（ADR-004）。

全部设计决策以编号原则 P0–P14 记录在 docs/PRINCIPLES.md，关键取舍各有一篇 ADR（docs/adr/）。本文按机制展开，重点是 §4 shim 与 §5 override。

§2总体架构：四条干预通道

包内分五层：compat/（L0，受治理的 monkeypatch）、kernels/（L1，昇腾算子的 @override 工厂）、graph/（L2，torchair 图模式）、models/+recipes/（L3，配置装配）、tools/（L4，矩阵/诊断/溯源）。但比分层更重要的是：本仓触碰上游的方式只有四条通道，每条各有自己的治理约束与生命周期。

核心取舍（ADR-001 / ADR-006）：不 fork 的代价是"上游一动我们就可能碎"，用三件事对冲 —— 按 SHA pin（P5）、nightly-first 基线让接口差最小化（P8）、以及下文所有机制在失效时响亮报错而不是静默漂移。

§3启动序列与副作用治理

import ascend_titan 本身无任何副作用（硬规则，tests/unit/test_import_purity.py 强制）。全部副作用集中在一个函数 _bootstrap.setup()，而它必须先于第一次 import torchtitan 运行 —— 因为 torchtitan/tools/utils.py 在模块导入时就冻结 device_type，只有 torch_npu 已把自己注册为 privateuse1 后端，冻结的值才是 "npu"。入口 python -m ascend_titan.train 存在的意义就是保证这个顺序。

环境开关 ASCEND_TITAN_SKIP_SHIMS=1 关闭全部 shim（golden 门禁用它证明"NIGHTLY 上不靠任何 shim 也能过"），=a,b 跳过指定条目（用于验证某个上游修复是否让 shim 变得多余）。

§4shim 机制（L0 compat/）

shim 是受治理的 monkeypatch：当上游代码没留任何配置开关（P0 先查开关！）、问题又归因为 TT/TORCH 且在 NIGHTLY 上复现（P8）时，才允许用 setattr 包装一个上游属性。治理的关键在于：注册即校验、应用即留痕、上游修好即删。

4.1 结构

4.2 三种 kind 的语义

  • wrap（默认，P3）：fn(original) 拿到当前实现并必须调用它 —— 外层加行为、内层跟着上游走，上游改进自动继承。
  • replace：整体换掉，会静默丢失上游后续改动，所以必须书面回答"为什么包不了"（why_not_wrap），并在 docs/upstream-tracking.md 写明什么上游改动能让它被删。
  • polyfill：补一个上游还没有的属性（典型是 nightly-only API），fn(None) 返回实现；属性一旦存在整条自动跳过 —— 升级 torch 后无需改代码，shim 自然失效。

失效检测是双向的：目标属性不存在时（上游移走/改名），apply_all 抛 ShimError 并直接在报错里给出处置指引（"查 upstream 链接，重定向或删除"）—— 绝不静默跳过，那会让 shim 变成暗债。

4.3 实例

@shim(
    target="torchtitan.distributed.utils:set_determinism",
    reason="确定性模式下上游把 flex 编译掉，这条路在昇腾上不通；"
           "上游对 ROCm 的处理就是改走 eager，昇腾缺这条分支",
    upstream="draft:docs/issues/torchtitan.md#deterministic-flex-on-npu",
    kind="wrap",
)
def flex_eager_when_deterministic(original):
    def wrapper(*args, **kwargs):
        result = original(*args, **kwargs)   # 先跑上游，再补差异（P3）
        ...                                  # 把 eager flex 装回去
        return result
    return wrapper

注意 upstream 用的是 draft: 形式：按 P10，github.com/pytorch/* 只读，不能真提 issue，于是链接指向 docs/issues/ 里已起草好的 issue 正文 —— 治理约束（每条 shim 必须挂上游问题）在授权边界内仍然成立。

§5override 机制（L1 kernels/）

override 是 torchtitan 自己提供的扩展点（torchtitan/config/override.py）：在配置树构建之后、build() 之前，把任意 Configurable.Config 节点换成替代实现的 Config —— 不动上游任何代码。本仓的全部昇腾融合算子（attention、rope、rms_norm、swiglu、situ_glu、gdn、gdn_fla、kda）都通过这条通道接入，这也是 P6 的含义：只 override 上游已有的 Config 节点；计算没有节点时，推动上游抽一个出来，而不是替换父块（替换父块 = fork 了那个块）。

5.1 结构

5.2 应用流程与冲突模型

冲突模型是按节点而不是按类的：同一个 Config 类的两个 override 只要 fqns glob 不相交就可以共存（比如"只在后半层用融合 MoE"）。祖先规则在本仓有个真实案例（OURS-9）：上游 fused_mla override 认领整个 layers.N.attention 块，是内层 attention 节点和 RoPE 节点的共同祖先 —— 所以 transforms.npu_minimal 检测到这类块级 override 时，会同时跳过我们的 attention 和 rope 两条 override，并在 Applied.notes 里说明原因。

5.3 本仓侧的写法约束

# kernels/rms_norm.py —— 最小完整实例
from ascend_titan.kernels._probe import require_op, torch_npu

require_op("npu_rms_norm")          # P14：缺算子在 import 处抛 MissingNpuOpError

class AscendRMSNorm(RMSNorm):        # 子类化上游模块，参数名/形状/权重布局不变
    class Config(RMSNorm.Config): ...

    def forward(self, x):
        if self.weight is None:
            return super().forward(x)   # 内核要 gamma，无仿射时走上游
        return torch_npu.npu_rms_norm(x, self.weight, eps)[0]

@override(target=RMSNorm.Config, description="RMSNorm via torch_npu.npu_rms_norm")
def npu_rms_norm(cfg: RMSNorm.Config) -> AscendRMSNorm.Config:
    return derive(cfg, AscendRMSNorm.Config)

规则集中在 .claude/rules/kernels.md，要点：

  • drop-in 契约。替代实现保持参数名、形状、checkpoint 布局与上游一致；确需改布局时用 state_dict hook 桥接（参照上游 fused_swiglu）。
  • 自定义计算走 torch.library.custom_op，带 register_fake 与 register_autograd，配 opcheck 测试和对上游 eager 实现的对拍测试。典型收益见 kernels/attention.py：npu_fusion_attention 需要 host 端的序列偏移，.tolist() 在编译区里会变成 unbacked SymInt 破坏 tracing（OURS-8）—— 把 D2H 收进 custom_op 内部，对 dynamo 不透明，编译与 eager 同一条代码路径。
  • 依赖分两级（P14 / ADR-004）。torch_npu 与其算子是基础依赖：require_op 缺失即抛，错误信息直接指向 P9 流程（"这是昇腾侧缺口，去修 torch_npu，不要在这降级"）。只有需要单独构建、不在基线内的加速包（ops-nn、fla-npu、Triton-Ascend）走 optional_module + WARNING 降级，且降级必须被 provenance 记录（P7）。

§6配置装配：recipe 与 transforms（L3）

override 决定"节点换成什么"，L3 决定"哪些配置带哪些 override 跑"。布局按内容/机制切开：每个模型一个包 models/<model>/（recipes.py 支持入口 + 可选 probes.py 测量探针 + 必需 README），跨模型机制在 recipes/（transforms.py、动态矩阵 recipe）。models/registry.py 是纯数据的模型状态表（R1–R8 判据逐项记录，不 import torch）。

6.1 recipe：增量，不是拷贝

def qwen3_debugmodel_npu() -> Trainer.Config:
    config = qwen3_debugmodel()          # 必须调上游函数起手（test_recipe_is_delta_not_copy）

    # DELTA 1: varlen 注意力节点 + 昇腾融合注意力 override（矩阵格：attention/ascend_fusion）
    config.model_spec = model_registry("debugmodel", attn_backend="varlen")
    config.override.imports = [ATTENTION_OVERRIDE]

    # DELTA 2: 冒烟运行不做 checkpoint I/O（DCP-on-NPU 是独立矩阵格）
    config.checkpoint.enable = False
    return config

每条增量带 DELTA n 注释、对应一个矩阵格。参考路径（qwen3）现在距离 stock 上游只有这两条增量 —— 这是 P12 持续收缩的结果：凡是版本差造成的增量都随 nightly-first 删除，golden 重录后逐位一致。

6.2 npu_minimal 与 npu_fused 的分界（P12）

  • npu_minimal：只含"不加就跑不起来"的增量，矩阵默认施加。当前两条：flex→varlen 节点转换（按特性探测门控 —— 设备白名单已解除且 inductor 有可用后端才保留 flex；探测函数注明 issue ID 和消失条件）、复数 RoPE → 实数 cache（NPU-3）。目标态是恒等变换。
  • npu_fused：性能 override（融合 RMSNorm、融合 GDN 等），永远 opt-in（--mode fused）、永远不进测量基线 —— 否则红格分不清"上游问题"还是"我们的内核问题"。数值与非融合路径差在 bf16 舍入级，融合 recipe 因此各自持有 golden。

§7四种手段对比与失败归因

手段作用点什么时候用治理约束生命周期
recipe / transforms 配置数据 上游已有开关或节点可选（P0 首选） 增量必须可审计（DELTA 注释 / issue ID / 特性探测消失条件） minimal 目标 = 恒等变换
override 配置树节点 用昇腾实现替换某个 Configurable 节点 只打已有节点（P6）· drop-in 契约 · 对拍 + opcheck 长期存在（这是正当的扩展点）
shim 上游代码属性 TT/TORCH 缺陷，NIGHTLY 复现，且无开关 upstream 链接必填 · 默认 wrap · replace 要 why_not_wrap 上游修好即删（现存 3，目标 0）
patch torch_npu / op-plugin 源码 NPU 归因缺陷（唯一合法处置，P1/P9） 最小复现 + UT + 构建验证 + gitcode issue/PR + STATUS.md 合入即删，升 torch_npu.sha

§8支撑系统（L4 与仓库层）

  • 能力矩阵（tools/matrix/：triage / cases / runner / report / cli）：把上游 tests/integration_tests 的用例搬到 NPU 批量扫描，产出三态格子（🟢 / 🔴 附归因 / ⚪ 未评估，P2）。2026-08-30 全量：61 用例 28🟢 / 28🔴 / 5⚪，红格归因全部为外因（CANN、DEP），NPU/OURS 类为 0。归因规则是数据（triage.toml），加规则不动 Python。
  • golden 曲线（tests/assets/losses/npu/）：确定性模式下逐位冻结的 loss 曲线，文件名带完整版本元组；check_golden.sh 在 ASCEND_TITAN_SKIP_SHIMS=1 下运行 —— 基线正确性不依赖任何 shim。
  • provenance（tools/provenance.py）：运行时枚举实际生效的 Ascend 节点与降级情况；没有 provenance 表的 benchmark 不收（P7）。
  • 版本三元组（constraints/）：nightly.txt + torchtitan.sha + torch_npu.sha 是唯一事实来源（P11）；三者一起升级，走附带全量矩阵结果的 PR（P5）。
  • 问题状态：唯一事实来源是 docs/issues/STATUS.md，其它文档只引用 ID；tests/unit/test_patches_and_status.py 强制每个在途补丁头部携带 issue/PR 链接且与 STATUS 行一致。
  • CI：ci.yml（CPU 单测 + lint）与 npu-nightly.yml；NPU 侧真机验证依赖开发容器 8× 910B2。

§9不变量与强制机制

原则不靠自觉，靠测试和注册表在结构上强制 —— 这是本仓设计里最值得保留的部分：

不变量原则强制机制
import ascend_titan 无副作用—tests/unit/test_import_purity.py
每条 shim 挂上游链接；replace 必须说明P3 / P4@shim 装饰器 import 时抛 ShimError
shim 目标失效必须暴露P4apply_all 对缺失属性抛错并给处置指引
recipe 是增量不是拷贝—test_recipe_is_delta_not_copy（禁止从零构造 Trainer.Config）

§10已知薄弱点

2026-09-01 评审结论：架构判断（薄插件、不 fork、响亮降级、nightly-first）无需返工。评审列出的债务已在 2f072d3 / 1722809 两次简化中清理，下面是清理内容与仍然开放的判断题。

已清理

  • override 路径常量收敛到 kernels/__init__.py 唯一定义（原先 5 处字面量），test_override_paths 双向防漂移——首跑即抓到 kimi_k3 一个从未使用的死常量。
  • tests/repro/ 生命周期落地：30 个文件删到 4 个，保留的每个都在 README 里写明挂靠的 issue / 文档，挂靠失效即删；一次性探索脚本改进 outputs/（gitignore）。
  • 判据漂移堵上：ModelEntry.graded_status 原本是死代码，现在是 table() 的取值来源；两条新不变量测试要求手写 status 等于 R1–R8 推导值、且有判据的模型必须指向真实存在的证据文件（首跑即抓到 qwen3_5 漏填 evidence）。
  • 重名 Applied：recipes/transforms 的那个改名 TransformReport。
  • 重复条件与重复代码块：_bootstrap 里 device_type != "npu" 判两次（前 raise 后 warn）合并为一处，死 warning 与恒为 True 的 torch_npu_imported 字段删除；registry.apply_all 的重复报错文案与 polyfill／wrap 两条重复的记账尾巴合并；transforms 三处"未存在就追加"收敛为 add_override()。
  • 违规兜底：bench.py 不再吞 provenance 异常（P7：没有 provenance 表的基线不是结果）；_bootstrap 删掉 nightly 基线上不可能触发的旧 torch 兜底（P8）。死函数 registry.applied()、ModelEntry.has_package 删除。

仍然开放

  1. _KEEP_FLEX_FQNS 用 fqn 子串匹配视觉塔。上游改名即静默失效；更稳的是按 mask 类型（BlockMask）探测。矩阵扫描能兜住，优先级低。
  2. kind="polyfill" 在本仓被 CI 禁止（test_no_polyfills_remain：nightly-first 之后不该再有为旧 torch 补 API 的 polyfill），机制却仍保留。这不是疏漏而是刻意：迁移目标 TorchTitanTurbo 的 graph_trainer/_compat.py 正在手写这类补丁，polyfill 是它需要的受治理形式。删与不删取决于迁移后的版本 track。
  3. qwen3_5/probes.py 的 lr 夹逼实验（lr_5e4 / lr_1e3）只有 CLI 入口、无文档引用。成对保留，等那个 lr 问题结论落到 docs 后一起删。
