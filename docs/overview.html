torchtitan · 昇腾 910B2 · 树外扩展

ascend-torchtitan 现状

结果、判断、以及未来会撞上什么。把 torchtitan 跑在昇腾 NPU 上，方式是扩展而不 fork—— 上游按 commit SHA 固定为已安装依赖，我们只加 shim、override 和 recipe。

我认为的精华

按"抽掉它会怎样"排序，不是按代码量。排在最前的两块都不是算子。

承重

对上游 Configurable 节点做 override

这是整个项目能成立的前提，也是"扩展而不 fork"这句话的全部技术含量。

torchtitan 把每一处计算都暴露成配置树上的一个节点。于是替换 fla 的 CUDA 内核、替换 RoPE、替换 SwiGLU，都不需要动一行模型代码—— derive() 出一个新配置，装配点只有 recipe 里的一行 override.imports。 如果上游没有这套机制，这个仓库只能是一个 fork，然后死于每周的合并冲突。

配套的两条约束同样重要：只 override 已有的节点（没有节点就请上游抽一个，而不是替换父块）， 以及按实例选择通过 fqns= 表达而不是在工厂里 if。前者防止我们悄悄 fork 一个 block，后者让生效范围可审计。

承重

判据 + 证据纪律

这是让仓库的结论可信的东西，也是唯一能对抗自欺的机制。

R1–R8 把"支持这个模型"从一句形容词变成八条要出示命令与输出的断言；provenance 表证明跑的是声称的实现； 三态里"没测"和"测了不行"永远不共用一格。

它的价值不是理论上的。仅这一轮它就推翻了仓库自己的三条既有结论：Kimi K3 的绿复测不再复现、 TT-11（"cutlass 是 CUDA-only"）证伪、DEP-FLA（"fla 装不上"）证伪。 没有这套纪律，这三条错误认知会一直躺在文档里指导后续决策。

承重

归因机制与上游边界

让红格从"沮丧"变成"工单"。

每个失败都要落到一个代码：NPU / TT / DEP / CANN / HARNESS。 归因规则是数据（triage.toml）不是代码，新增一条不用改 Python，还能对历史结果离线重算。

更关键的是两条不容商量的边界：torch_npu 的缺陷只能修不能绕（在本仓任何位置绕过都是违规）， github.com/pytorch 只读。这让"这个坑归谁"永远有答案，也让本仓不会长出一堆越活越久的 workaround。

有价值

工具链：matrix / release_check / bench / provenance

普通工程，但没有它就拿不到证据。

把上游 tests/integration_tests 的用例搬到 NPU 上批量跑并自动归因，把 R1/R2/R4 变成一条命令， 把性能数字和"生效的实现"绑在一起。这些不是洞见，但它们决定了取证的成本——而取证成本决定了判据能不能坚持下去。

可替换

kernels/ 里的算子实现

工作量最大的一层，恰恰是最该被替换掉的一层。

attention / rope / rms_norm / swiglu 本质是薄封装；真正有原创数值内容的只有 GDN 与 KDA 的 chunk 递推， 而它们存在的理由是"昇腾还没有对应的融合算子"。flash-linear-attention-npu 一旦接上， 这一层里最重的部分应该退化成适配器。

把大量精力投在这里是阶段性的必要，不是长期资产。

哪些工作是 trivial 的

说清楚这个不是贬低，是为了不把它们当成进展来汇报。

recipe 本身

一个 recipe 就是三到五行增量：换个 attn_backend、加一行 override.imports、换数据集。 这是刻意设计的结果（增量越少，红格的归因越干净），但写一个 recipe 不构成智力工作。新增模型的真实成本在验证，不在 recipe。

shim 层

目前只有两条，在 NIGHTLY 上都自动 no-op。这一层被设计成会萎缩到零——投在这里的努力按定义是临时的。 删掉一条 shim 是值得庆祝的 PR，这句话不是修辞。

debugmodel golden

最便宜的回归探测器，但探测能力很弱。这一轮的实证：0.8B 在真实尺寸上发散时 golden 全绿； 而修掉那个发散的求逆改写，golden 逐位不变。它能抓装配错误，抓不到真实尺寸下的数值问题。 不该把它当成质量保证。

文档与表格维护

状态表已经改成由 registry.py 生成而不是手抄，这类机械劳动应该继续往工具里赶。 RELEASE track（torch 2.13）目前是纯负担，只做信息性报告，应当退役。

风险与困难

按"卡住什么"和"什么能解开"两列看。前三条不是这个仓库能自己解决的。

风险它卡住什么什么能解开程度
拿一个失败的运行推广成通则 方法论风险，排第一是因为它已经咬过我们一次。视觉塔的 flex 曾被连着三次错误归因—— "910B2 缺 indirect-memory lowering"、"flex 自己会编译所以无解"、"Kimi K3 硬件级阻塞"—— 全部写进了仓库并发布。真相是：只在 --debug.deterministic 下失败， 因为 torchtitan 的 set_determinism 会重新编译并覆盖我们装的 eager shim， 而上游只为 ROCm 写了 eager 分支。补一条 shim 就修好了，两个模型的 golden 现在都冻结了。 单变量对照，一次只切一个开关。判据体系能抓住结论错，但抓不住归因错—— 归因错要靠这个习惯。 高
线性注意力的性能是结构性缺口 GDN / KDA 走纯 torch 的 chunk 递推，两层串行循环（每文档一次 × 段内每 chunk 一次）， 循环里每个算子还要过 activation-checkpoint 的 dispatch mode。步时被 Python 派发次数支配，不是算力。 实测 245 tps vs Qwen3 的 10,186 tps——40 倍差距，且不是靠改数学能补的。 昇腾侧的融合算子（flash-linear-attention-npu 已在同级目录，未接入）， 或把 GDN 子图整体交给 torchair 图模式。 高
行业正在往线性/混合注意力走 上一条的战略含义。Qwen3.5、Kimi 这一代都是 GDN / KDA + 稀疏注意力的混合结构。 我们的性能故事恰好在行业前进的方向上最弱：稠密注意力有融合算子且跑得好，线性注意力慢 40 倍。 同上，且优先级应当高于"再多支持几个稠密模型"。 高
基线是一个我们不控制的移动目标 torch_npu 从 master 源码构建、带 8 个在途补丁。每次重建都可能静默改变行为—— 这一轮就出现过：Kimi K3 的绿在 wheel 重建后消失，而本仓提交没动过相关代码。 上游 torchtitan 也在 pre-1.0 阶段重构配置树，override 的目标节点可能改名或改语义。 节点改名会在 import 时炸（可接受）；改语义不会——只能靠对上游 eager 的对拍测试兜住。 这类测试目前覆盖不全。 高
取证成本随模型数线性增长 一次真实尺寸的验证 15–60 分钟，R1–R8 全套要几小时。让仓库可信的纪律，同时也是迭代速度的上限。 这一轮验证一个假设 = 15 分钟，逼出了"把出问题的张量抓下来离线迭代"的做法。 需要真正有效的廉价代理（现在的 debugmodel golden 不是），以及跑在真实 runner 上的 nightly CI。 中
没有 GPU 做交叉验证 我们能证明"自己与 attn_gym reference 一致"，证明不了"reference 与 fla 的真实内核等价"。 线性注意力这一族的数值正确性因此存在一个无法闭合的环节。 一张能跑 fla 的 CUDA 卡；或接入 fla-npu 拿到昇腾上的第二实现来互证。后者更现实。 中
共享单机 8 张卡与其他作业共享。同卡并发 HCCL 直接报错，CPU 争用会污染步时测量—— 这一轮有一次性能对比就是被自己并发的任务毁掉的。 工程上已有缓解（按卡集分配 HCCL 端口、卡表强制升序），根本上需要独占资源。 低
知识密度 真正会咬人的知识是分散的细节：LR 曲线绑在 training.steps 上、PP 下只有最后一级算 loss、 卡表必须升序、步时被派发次数支配。它们目前活在 docstring 与几篇文档里。 已经在做的：把每个坑写进它所属的工具而不是一篇通用文档。这条要持续。 低
最容易被低估的一条：让人栽跟头的从来不是"跑不起来"，而是跑得完、有输出、但结论是错的。 这一轮清掉六条这样的坑（LR 曲线耦合、checkpoint 目录相对解析、PP 下记录 rank 0 拿到占位符、 多卡卡表原样进环境变量、报告标错步号、数据集看起来卡在 step 0）。 它们都不会报错，只会安静地给出一个错误的判断。防它们的唯一办法是：任何结论都要能说出它的证据是哪条命令的哪一行输出。

Roadmap

按门槛分期，不按时间承诺。每一期的"解锁条件"是进入下一期的前提——顺序不能调换。

第一期 把线性注意力做实
解锁条件
fla-npu 装上并通过对拍
  • 接入 flash-linear-attention-npu —— 同级目录里就有一份 AscendC 实现的 GDN / KDA 算子库。它一次解两件事：R5 的 40 倍性能差距， 以及给我们的 chunk 递推一个独立于 attn_gym 的第二实现来互证。这是当前投入产出比最高的一件事。
  • 补齐 Qwen3.5 的 R2 / R4 / R6 —— TP / PP / EP 未测；DCP 续训要先有一个冻结视觉塔的机制（上游目前只有 LoRA 自己做）； R6 长稳被 R5 卡住，一步 67 秒跑 500 步要 9 小时。这三条里有两条依赖第一件事先落地。
  • 退役 RELEASE track —— torch 2.13 那条线目前只做信息性报告，是纯维护负担。
第二期 把取证成本压下来
解锁条件
nightly CI 跑在真实 runner 上
  • 真实 runner 上的 nightly —— 矩阵扫描 + release_check 现在都是手动触发。变成每晚自动跑，才能在 torch_npu 重建导致回归时当天发现， 而不是几周后复测时才发现（Kimi K3 就是这么丢的）。
  • 找到有效的廉价代理 —— debugmodel golden 抓不到真实尺寸的数值问题，这一轮已有实证。需要的是介于两者之间的东西： 比如固定输入下的逐层激活范数快照，或者算子级的极端输入压测（已经有雏形）。
  • 对上游 eager 的对拍覆盖到每个 override —— 防的是上游改语义而不改名字这种静默漂移。目前覆盖不全。
第三期 扩模型覆盖
解锁条件
前两期就位，单个模型的验证成本可控
  • 从 4 个专属 recipe 扩到上游主力集 —— DeepSeek-V3、GPT-OSS、Kimi K2.7 目前只有矩阵覆盖。加 recipe 本身是 trivial 的， 成本全在取证——所以必须等第二期把成本压下来再做，否则只是把一堆 ⚪ 变成另一堆 ⚪。
  • Qwen3 的其它尺寸 —— 1.7B / 14B / 32B / 30B-A3B。14B 在 8×910B2 上已确认装不下，更大的尺寸要先解决显存配平 （bf16 优化器状态、更激进的重计算）。
  • MoE / EP 的深度覆盖 —— 矩阵里 fsdp+ep 已绿，但没有一个 MoE 模型走完 R1–R8。
第四期 硬件相关
部分需 Ascend950；
CP 那条只需重测
  • 上下文并行重测 —— 此前判定"910B2 上不可能"的前提（flex 编不出来）已被推翻，需要按实测重走一遍。 CP 还有 TT-5 等其它约束，前提没了不等于它就能跑。
  • FP8 —— 910B2 上张量能分配，但所有转换失败、_scaled_mm 明确要求 Ascend950。 按"不加投机性代码"的原则，post-converter 树上的 FP8 override 至今没有写——没有硬件就无从验证。
贯穿始终的一条：kernels/ 应该越来越薄。今天它是仓库里代码量最大的部分， 但每一个昇腾侧融合算子成熟，就应该有一段自研数值代码退化成适配器。 如果三年后这一层还在长大，说明昇腾的算子生态没有跟上——那才是这个项目真正的长期风险。

什么会让这个项目失败

纪律先松，然后全盘不可信

只要开始接受"应该可以"的推断、接受没有输出的绿格、接受一次"临时绕一下"的 workaround， 整张状态表就会退化成愿望清单。这一轮推翻的三条旧结论说明：连有纪律的时候都会错， 没纪律的时候只会错得看不出来。

被算子生态拖住

如果昇腾侧的线性注意力算子迟迟不成熟，我们就得一直自己写数值代码—— 而自研数值代码正是这一轮出问题的地方（Neumann 级数在真实训练输入上溢出）。 自己写得越多，这类隐患越多。

把"暂时不会"当成"永远不能"

视觉塔那条错误归因差一点就让 Kimi K3 与 Qwen3.5 的多模态路径被永久记成硬件阻塞、不再有人回头看。 一条写进文档的"不可能"会让后续所有人停止尝试——它的成本远高于一次红格。
